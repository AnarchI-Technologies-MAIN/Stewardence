# Core recovery contract

Recovery is deterministic and bounded. It can repeat an admitted operation or reconcile recorded facts; it cannot manufacture evidence, grant access, bypass payment rules, rewrite immutable snapshots, or run arbitrary shell commands. Customer consent to a provider connection does not authorize provider writes.

## Implemented in the local candidate

- Known network timeouts/connection failures and renderer HTTP 408/429/502/503/504 are eligible for existing bounded queue retries. Queue delays are one minute, five minutes, thirty minutes and two hours; the fifth failed attempt stops.
- Authorization, validation, configuration and unclassified failures stop with a review-required status. Persisted errors use fixed safe messages and fingerprints; raw exception details do not enter client views.
- Expired worker leases are rejected before persistence. The job row is locked through publication metadata and completion in one transaction, preventing stale workers from committing metadata after losing ownership.
- Expired leases recover through the existing queue mechanism; completion remains fenced by worker identity, claim token and expiry.
- Repeating report generation reuses a failed job rather than silently creating fresh attempts that evade a review hold.
- Report pages show queued/preparing/review-required states, preserve the browser report, and offer PDF downloads only when artifact metadata exists. Downloads still verify original bytes against stored size and hash.
- Atomic object creation prevents competing report writers from overwriting originals. Identical objects are idempotent. Conflicting objects stop for review.
- A database metadata failure retains the private uploaded object rather than deleting it after releasing the database lock. An identical-byte retry can reconcile metadata safely. Orphans with unavailable provenance or different regenerated bytes require review; they are not silently adopted.

No production worker has been started. These are source and local-test capabilities, not proof of an active recovery service.

## Remaining gates before enabling recovery

- Durable publication receipts and audit events recording admitted recovery actions, attempt/failure category, tenant, resource identity and outcome without secrets.
- Controlled operator review/resume actions with tenant/owner authority, expected state and audited exact scope; no public arbitrary retry endpoint.
- Per-dependency circuit breakers, retry timing/jitter policy, health/backpressure metrics and actionable owner alerts; distinguish outage from invalid evidence.
- Verified private storage, backup/restore rehearsal and resource checks on the existing Droplet.
- Crash-injection qualification across external upload, database commit, job completion, lease expiry and process restart.
- Client recovery experience/accessibility and actual PDF delivery qualification.

Automation development remains gated behind Core's required acceptance criteria in core-hardening.md. Core recovery does not enable scheduled provider collection or purchases.
