# Current-candidate restore qualification: bounded next steps

Read-only source review while the final coverage run is active. No backup, container, object deletion, remote operation or service change was performed. This plan distinguishes existing historical evidence from proposed current-candidate execution.

## Existing useful evidence and limitations

`docs/report-object-recovery-qualification.md` records recovery of an encrypted database backup and six actual private PDFs from Ubuntu WSL ciphertext custody, with artifact ownership/hash/length checks and actual-role private request tests. It also records the accepted exact image, bounded cleanup and the important limitation that fabricated subscriptions were disposable positive controls. That older image and backup predate current paid-coverage authority, capture/proposal/decision receipts and pack v4. They cannot qualify the latest source merely because old data restores successfully.

`scripts/qualify_live_restore.py` reads a live database dump through SSH, encrypts before host persistence and streams decryption into an isolated target. `qualify_report_object_restore.py` pins an older database summary and verifier image, checks live artifact metadata against that encrypted snapshot before fetching existing objects, then encrypts private manifest/object content. `qualify_restored_report_access.py` / `restored_report_access_probe.py` replay older restored private-read/corruption/tenant cases. These are valuable predecessor contracts, but are unsuitable to run unchanged as an offline current-candidate qualifier: some paths contact the live server/bucket and assume three historical roles. Do not silently rewrite their pinned accepted receipts.

Windows key custody and Ubuntu ciphertext custody share one physical machine. The Droplet is a different machine, but a local WSL restore alone does not establish device-loss survival, independent offsite custody, credentials recovery or production recovery time. Weekly Droplet snapshots are separate reported evidence, not verified object/database recovery by these scripts.

## Proposed smallest current-candidate exercise

1. Add a separately versioned local-only harness, retaining the older scripts/evidence. Pin the same frozen candidate source/image/migration catalog used by final qualification, plus the actual renderer image where the HTTP path is used. Use the four scoped database roles, forced RLS and current account/mode/price authority pins from explicit synthetic setup. No historical coverage backfill or projection-only subscription substitute.
2. Generate two genuinely admitted local journeys, generic and qualified accounting: paid test receipt → capture → admitted proposals → owner disposition and unverified completion statement → frozen v4 → actual HTTP Chromium → private PDF → committed PackCompletion. Verify owner retrieval and same-tenant viewer/cross-tenant denial before backup. These synthetic customer records are qualification data, not provider-paid production customers.
3. Before the disposable source is torn down, take its logical database dump and bind the exact stored PDF objects to an encrypted private manifest containing report/artifact/snapshot/request/pack/completion identities, hashes, sizes, deterministic keys and source/image/migration pins. Stream database/object bytes directly to encryption; avoid plaintext dump/PDF persistence on the Windows host. Keep the recovery key only at its existing approved Windows custody location. Store ciphertext under the approved Ubuntu WSL backup directory. Public receipts contain counts, bounded sizes and ciphertext/source hashes, not customer data, tokens, key values or private identifiers.
4. Restore into a fresh disposable PostgreSQL target, provisioning exact roles without privilege shortcuts. Compare migration catalog, ownership/ACL entries, forced-RLS flags, role superuser/BYPASSRLS denial, admitted paid receipts, immutable snapshots and every report/request/completion binding. Do not run successor migrations silently during an “exact-image restore”; if migration compatibility needs testing, label it a distinct stage.
5. Restore bound objects into an isolated private backend without altering original immutable metadata. Retrieve each through current actual-role application middleware/views, preserving owner-only v4 classification and current paid authority. Require exact PDF hash/size, completion/manifest validation and private/no-store delivery. Prove anonymous/viewer/cross-tenant denial before storage, missing object rejection, changed-length and same-length hash corruption rejection, and successful recovery of the same object identity after replacing only the disposable damaged copy.
6. Keep legitimate expired-paid read coverage as a separately labeled fixture stage: use truly past admitted test intervals and the current 90-day predicate, not timestamp mutation, bypassing coverage guards or asserting that a pack was historically admitted while expired. The archive-read fixtures already distinguish synthetic persisted rows from executed historical admission. A DB restore must preserve this distinction.
7. Withhold success until exact-owner/label cleanup and absence checks complete for every target and internal network. Retain failed ciphertext/hash/decrypt/restore/access/cleanup attempts, rather than replacing their receipts. Record source/harness/image identities and all executed stage counts. No device-loss or production readiness claim follows from this finite local exercise.

This requires an additive harness stage that captures qualified objects before current pytest temporary directories and the disposable database disappear. Merely rerunning the existing tests and then looking for their deleted temporary PDFs cannot produce a complete recovery backup.

## Retention and capacity gates remain separate

The existing retention audit identifies no qualified physical object-expiry executor or append-only object availability/deletion ledger. Immutable metadata, delete acknowledgments and billing access expiry are different contracts. Do not delete objects, release accounted bytes or resurrect expired availability as part of restore qualification. Restore must eventually reconcile expiry receipts and restored older objects, but until such receipts exist that is a proposed successor test, not current functionality.

Before enabling a retention executor, resolve calendar-month versus fixed-day history windows, verified-completion versus capture-date anchoring, export grace versus rolling history, pinned baselines, explicit holds, and separate billing/security/legal metadata retention. Confirm all enabled report writers are capacity admitted. Storage errors need typed not-found versus forbidden/network/ambiguous deletion and replacement-generation outcomes before any deletion can safely release capacity. These decisions do not block a bounded nondeleting local recovery test; they do block claims of fully implemented 12-month physical retention or automated erasure.
