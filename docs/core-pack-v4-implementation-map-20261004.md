## Selected proposals: identity and issuance

Each selected-proposal entry has exactly `proposal_receipt_id`, `revision_id`, `revision_sha256`, `card_index`, `card_sha256`, `qualification_sha256`, `proposal`. `proposal` is the complete immutable v1 proposal object, including its existing `sha256` field, not a paraphrase or regenerated current-policy card. Receipt identity and all digest/foreign-key relationships must resolve to the actual issued same-tenant revision/capture before freeze.

There are two different hashes: proposal `sha256` hashes the proposal without its own hash; `card_sha256` hashes the complete revision card including that field. Preserve both and never substitute one for the other. `revision_sha256` hashes the complete issued array. Validate the selected index against the complete revision, receipt contract `stewardence.core_review_proposal.v1`, snapshot input/result, and permanent applicability qualification. A caller-computable correct hash is not issuance evidence.

Freeze all issued proposals for the selected capture as the initial supported scope; do not implement partial selection implicitly. Order by integer card index, require unique proposal IDs and indexes, and permit an actually issued empty revision. No decision is required for a proposal to appear: show “No owner statement recorded” instead of inventing an accepted/default state. Retain generic source class/identity/digest/definition digest and accounting rule version/definitions/applicability/qualification/policy-engine pins exactly as issued. Accounting severity is conditional on accounting proposal class; generic proposals have no invented severity.

## Selected decisions: separate owner statement snapshots

Each selected-decision entry has exactly `event_id`, `event_sha256`, `payload`. `payload` is the full immutable `stewardence.core_decision_event.v2` object issued by jobs 0016. Its closed keys are: `schema`, `id`, `organization_id`, `created_by_id`, `created_at`, `revision_id`, `revision_sha256`, `snapshot_id`, `snapshot_result_sha256`, `card_index`, `card_sha256`, `previous_event_id`, `sequence`, `event_kind`, `state`, `responsible_label`, `due_date`, `notes`, `links`, `owner_statement_only`, `resolution_verified`, `proposal_id`, `proposal_sha256`, `proposal_contract`, `proposal_receipt_id`, `source_class`, `source_identity`, `source_digest`, `original_outcome`, `resolution_effect`, `source_state_immutable`.

Require event ID equality, full payload digest, actual admitted event row and exact linkage to one selected proposal, revision, receipt and source. `sequence` is a positive integer; index is a nonnegative integer (booleans never accepted as integers). Preserve canonical UUIDs, bounded date/notes/reference validation, and UTC instants. States remain disposition `act/defer/decline/accept_risk` or execution statement `completion_recorded/evidence_reviewed`, with `owner_statement_only=true`, `resolution_verified=false`, `resolution_effect="none"`, `source_state_immutable=true`.

Minimal complete presentation requires the latest disposition and latest execution statement separately for each proposal, when present: selecting only the overall newest event loses an earlier disposition when a completion statement follows. Choose latest per `(revision, card_index, event_kind)` as observed atomically at freeze, sort by `(card_index, event_kind, sequence)`, permit zero to two statements per proposal, and reject duplicates. Freeze their full immutable bodies. Historical predecessor ID is a reference, not proof of the complete chain in this bounded export; the database admission boundary must validate actual history. Label both timestamps and statement kinds. Later owner statements cannot mutate an existing pack.

## Minimal additive authority interfaces

Add private helpers such as `review_capture_proposal_selection_v1(snapshot,org)` and `review_capture_decision_selection_v2(snapshot,org)`; additive `freeze_capture_proposal_review_cycle`, `validate_capture_proposal_pack`, and `capture_proposal_pack_projection`. Names are proposed, not presently existing APIs. Prefer explicit successor bodies over textual replacement of predecessor SQL. Extend public lifecycle dispatch only for v4; keep renamed predecessor helpers private and existing bodies unchanged.

Freeze must share the proposal-specific and decision-specific serialization protocol with their issuers. Control lock comes first; acquire remaining locks in a documented consistent order, protect referenced rows, and reread membership, entitlement, pause, profile and gates after the final wait. An append-only event table does not alone serialize a “latest event” selection. If acquiring all proposal decision locks is too broad, specify a shared snapshot-selection lock admitted by both decision issuance and freeze before implementing it. Do not silently change old Decision v1 ordering.

Projection must validate full frozen issuance bindings and admitted job/request/lease ownership before returning payloads. Request/completion preserve report-capacity reservation, receipt atomicity, verified private-object readback and claim-token/pause fences. Post-freeze new statements do not invalidate frozen selection; compare frozen events to their admitted rows, not to the current latest event. No new worker provider-table permissions or app raw-CRUD grants are needed.

Completion v2 may remain unchanged only if its existing exact artifact/request/manifest digest already binds the entire v4 manifest; otherwise add a separately versioned successor receipt, not loosen v2. Preserve private owner-only report classification and 90-day expired-paid export policy. Existing storage byte verification remains mandatory.

## Qualification gates and unresolved bounds

Required meaningful negatives: counterfeit revision without receipt; swapped same-tenant revision/index/proposal ID; proposal-hash vs full-card-hash substitution; rehashed source/rule/qualification substitution; event payload digest mismatch or swapped source/event; duplicate proposals/statements; v1 event on v4 proposal; unsupported enum/version/bool numeric fields; unselected event; cross-tenant/owner access; pause or paid expiry while waiting; promotion true; capacity exhaustion; worker stale lease; completion without verified object receipt. Test later decisions leave a frozen pack unchanged and that old v2/v3 golden contexts/PDF meanings remain unchanged under mutable alias patches.

Actual-role concurrent tests must prove freeze has one coherent event selection with no lost latest disposition, and final authority is rechecked after waits. Run actual worker → Chromium → verified storage receipt → owner HTTP private download, plus viewer denial before storage and retained historical read separately. Synthetic renderer consistency is not this admitted journey.

Proposal bounds need measurement before claiming supported capacity. Up to five generic proposals per record plus qualified accounting failures, two decision statements with 4096-character notes and ten 2048-character references each, can exceed the existing closed 1 MiB render envelope. Do not truncate an admitted frozen pack or enlarge resource limits without qualification. Preflight exact successor bytes at freeze and fail closed with an actionable receipt; define a supported record/statement allowance from representative workloads. Baseline comparison/promotion, complete event-chain export, partial selection, new evidence uploads, scheduling and verified remediation are outside this minimal successor.

The existing report identity permits one Report per snapshot, and ArtifactRequest binds a report to one pack. Once a v3 or v4 request has bound that report, another pack for the same snapshot cannot silently acquire a fresh report or reuse a PDF belonging to different frozen statements. The first supported journey is one deliberate capture → issued proposals → owner statements → freeze → report. A later report requires a fresh deliberate capture, preserving earlier history and requiring explicit new decisions rather than carrying completion forward. Explain this boundary in the UI. Do not expand report/artifact identity schemas merely to hide it; a separate qualified successor is necessary if that future journey becomes required.
