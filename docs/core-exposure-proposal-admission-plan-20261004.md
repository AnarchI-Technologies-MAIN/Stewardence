## Minimal additive contract

Use `stewardence.core_review_proposal.v1` and a permanent pure implementation module, rather than parsing free prose or dispatching through a mutable current alias. Each card contains a deterministic `proposal_id`, organization/snapshot/result identities, inventory/record identities, a closed source object and action, derived text, `authority=proposal_only`, `verification=not_established`, `source_state_immutable=true`, and `resolution_effect=none`. Generic cards omit severity/risk-score fields. Qualified accounting cards may copy the exact rule severity, without deriving an aggregate risk score.

The closed source classes are `exposure_unknown`, `exposure_concern`, and `accounting_fail`. Bind source contract and version, source identity, exact outcome, source fields, and canonical digest. For exposure, digest the complete normalized question object, including explanation/basis/verification; question ID alone is insufficient. Also pin the permanent exposure contract and full frozen record SHA. For accounting, bind exact policy result digest, rule identity/version, pinned definitions SHA, policy engine/known-premise wrapper, and the complete frozen applicability object SHA. Define a proposal-specific applicability contract/version that interprets those existing immutable pins; do not add fields retroactively to capture schema 2 or assert independent industry verification.

A stable proposal UUID can be derived from a fixed namespace plus snapshot UUID, proposal contract, inventory UUID, source class/identity/digest. Canonical proposal SHA covers its complete immutable payload excluding its own SHA, and excluding issuance wall-clock time. Receipt/revision creation time remains separate. Sort deterministically by inventory UUID, source class, source identity, and proposal UUID; never reuse an index as identity. New semantic versions require new issuance/version storage design, not substitution under v1.

The first implementation should have an explicit template allowlist: UNKNOWN responsible person/business purpose → `request_declaration`; UNKNOWN account identity/access removal → `request_evidence`; approval CONCERN → `review_declared_boundary`; qualified accounting FAIL → `address_qualified_failure`. PASS and NOT_APPLICABLE emit nothing. Exposure questions outside this initial allowlist remain visible as exposure questions; do not imply every unknown produces a task. If broader UNKNOWN/CONCERN templates are desired, settle their mapping before coding rather than inventing text dynamically. No generic severity, urgency, automatic due date, recurring task, account creation, provider command, purchase, or verified/safe/compliant claim is admitted.

## Smallest database change and authority boundary

Reuse ActionCardRevision and DecisionEvent storage; add one immutable forced-RLS `CaptureProposalAdmissionReceipt` linking organization, owner, capture receipt, snapshot and revision, proposal contract, source/input/result/revision digests, frozen applicability qualification digest, and issued time. Snapshot/revision associations are unique for this initial version. Owner-only app SELECT; no app INSERT/UPDATE/DELETE, worker SELECT/write/EXECUTE, billing access or PUBLIC privileges. Owner policies support SECURITY DEFINER helpers. Do not grant provider-table access to workers. Receipt presence is the new issuance marker; a self-consistent cards hash alone is not issuance.

A new narrow `issue_core_exposure_proposals(revision_id, org, actor, snapshot)` takes identities only: no caller proposal text, question result, severity, applicability, or digest becomes authority. It loads an actual admitted capture receipt and exact immutable snapshot, reconstructs source questions and permitted accounting FAIL semantics, builds closed proposals, then inserts revision and receipt atomically. SQL should perform the bounded permanent exposure-v1 recomputation and canonical comparisons, with representative cross-language equivalence tests against the pure Python implementation. This is a small translation of the existing finite question contract, not a new risk engine. If implementation instead computes in trusted Python, explicitly document that trust boundary and provide a narrowly privileged issuer principal; app-supplied JSON plus a digest cannot be described as database recomputation. The direct app principal must not be able to counterfeit question outcomes by calling the issuer.

Require actual app tenant/actor contexts, READ COMMITTED, paid owner/profile, pause/integrity, and an operator-only default-false proposal admission gate plus a default-false application exposure-proposal flag. Acquire control before proposal/snapshot admission serialization. Lock the gate row and every referenced actor/org/snapshot/capture-receipt/revision row that can wait. Prelock any implicit FK targets before final admission; recheck current clock, paid/profile/pause/gate after the last wait, immediately before effects. Concurrent issuance uses a snapshot/contract advisory lock and unique constraints, returning one exact receipt-bound revision. Replay validates all immutable pins and stored semantics; changed identities or source versions deny. Never fabricate receipts for historical rows.

Keep the old schema-1 issuer body under an owner-only renamed helper and introduce an explicit public dispatcher: schema 1 delegates unchanged; schema 2 directs only to the new gated issuer or denies on the old entrypoint; unknown schemas deny. Revoke helper EXECUTE from app, worker, billing and PUBLIC. Existing one-revision-per-snapshot uniqueness means preexisting incompatible schema-2 revisions are a fail-closed conflict, not an overwrite or automatic conversion. A later proposal contract revision needs an explicit successor schema/storage policy.

## Decision Desk and pack v4

Add a closed decision envelope/event v2 for receipt-admitted capture proposals. Require exact proposal UUID/SHA alongside revision/index/hash; derive source immutable outcome and `resolution_effect=none` from the issued proposal, not the caller. Preserve existing states and bounded user statements; due dates remain explicitly entered. Completion/evidence-reviewed events never mutate capture results, original UNKNOWN/CONCERN/FAIL, applicability, or proposal payload. The decision issuer prelocks FK targets and rechecks paid/pause/gate after all waits. Legacy schema-1 decisions retain their exact old body; old decision v1 must not admit capture proposals implicitly.

Introduce a new owner-only selection helper for issued capture proposals and latest exact-proposal decisions. Freeze a new pack v4, preserving every v2/v3 body and replay branch. V4 extends the v3 immutable identity with `proposal_contract_version` and `selected_proposals`, and uses explicit non-empty-capable selection scope. Each selected proposal pins proposal UUID/SHA and source class/identity/digest; each selected decision pins its exact selected proposal identity. Include proposals with no decision, not merely cards that have received a statement. Freeze once; replay reads stored selections and verifies immutable pins, never rereads current history. Keep baseline promotion blocked for this slice.

Add worker projection/render context successors with closed version dispatch. They expose only stored frozen selections and exact immutable payloads, revalidate canonical question/proposal/event bindings and snapshot origin, and deny missing, extra, substituted-current or verified-labeled content. Historical v2/v3 renderers remain permanent paths. Report/PDF wording separates evidence requests, declared-boundary review, qualified accounting findings, and later owner statements. Source calculations do not become verified truth. Worker completion remains storage-readback-qualified and lease/paid/pause/gate fenced after the final lock; metadata hashes do not prove artifact bytes.

## Qualification sequence and negative matrix

1. Pure contract: exact UNKNOWN/CONCERN mappings; PASS/N/A absence; no generic scores/severity; accounting FAIL only under frozen qualified accounting applicability; explicit provenance required for every rule premise; malformed type/boolean/null/unknown key; deterministic ordering/UUID/digest and no alias mutation. Accounting fixture under a non-accounting capture emits no accounting proposal.
2. Actual-role admission: raw revision/receipt writes denied; worker/billing/helper execution denied; owner tenant/context/profile/paid/pause/gate checks; raw schema-2 snapshot without capture receipt denied; changed record/question/result/definition/applicability SHA denied; arbitrary caller question/text/outcome denied; existing incompatible revision denied; concurrent issuance/replay creates exactly one receipt and revision.
3. Deterministic wait barriers: hold operator actor/org/snapshot/capture-receipt/gate/proposal row or admission advisory lock; block actual app issuer; revoke ownership/profile/paid coverage or disable gate while blocked; release; require no revision/receipt/decision/pack side effects. Test service and direct SQL paths, actual session roles and READ COMMITTED. Test all implicit FK targets, not only cooperative advisory locks. For worker persistence, expire/revoke the claim while waiting on request/report/artifact/head/reservation rows; completion/promotion/consumption must remain absent.
4. Decisions: exact proposal UUID/SHA/index/previous-event CAS; cross-tenant/foreign revision/stale predecessor denied; owner evidence statement remains unverified; frozen UNKNOWN remains UNKNOWN after completion; later independently admitted capture may produce another outcome without rewriting history.
5. Pack/delivery: v4 frozen proposal/event → later live event → replay retains original; proposals without decisions included; missing/extra/wrong/live-substituted selection and misleading verified label denied; unknown contract/schema denied; actual worker command resolver through projection/context/real Chromium/private storage readback/completion; HTML/links escaped and no network fetch; owner-only browser/PDF access even before request association; cross-tenant/viewer access denied. Retain exact-source full-suite receipts and separate live-storage recovery gates.
6. Regression: legacy schema-1 issuance/decisions plus pack v2 and capture pack v3 empty-selection dispatch are unchanged; ordinary report handler still delegates; no worker table/provider access expansion; no scheduled execution or provider writes enabled.
