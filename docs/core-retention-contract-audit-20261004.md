# Core retention and capacity contract audit

Read-only source audit, 2026-10-04. No deletion, role expansion, storage call, service activation or production change was performed. The executor below is proposed, not implemented or qualified.

## Existing contracts and gaps

| Surface | Current source | Missing for physical retention |
| --- | --- | --- |
| Private storage | `reports/storage.py`: deterministic tenant/snapshot/report key, conditional private put, bounded get, local unlink and S3 delete-object | Typed absence/unknown result, read-back confirmation, object generation/version identity, complete deletion policy and executor |
| Report identity | Immutable Report and ReportArtifact identities, protected FKs and database mutation guards; artifact retains hash/size/key | Append-only lifecycle receipt separating retained metadata from available bytes; no approved physical metadata purge |
| Pack lifecycle | Immutable request/completion, verified readback, reservation events and baseline head | Expiry classification, missing-object reconciliation, tombstone read semantics and baseline handling after expiry |
| Export | `billing/0006`: any owner-visible admitted receipt with service_start <= database clock and service_end + 90 days > clock, matched account/mode/current customer | Object-specific retention eligibility, expiry notice/export accounting and independent archival policy. Pin removal/rotation denying access is not authority to erase data |
| History | Reports/review histories retain/query recorded identities | Rolling 12-month visibility and physical cleanup are not implemented |
| Capacity | Freeze reserves 16 MiB, counts 12 reservations in the admitted exact service interval, caps artifact bytes plus outstanding reservations at 3 GiB | Final workload-approved allowances, all-writer admission, verified-deletion byte release, orphan/reconciliation accounting |

The local delete returns success when absent. S3 delete acknowledgment does not establish that all stored bytes or previous object versions are gone; subsequent get failures also conflate absent with inaccessible unless errors are classified. A delete response lost after success is ambiguous and must not create a second deletion identity or release capacity prematurely. No live DigitalOcean deletion semantics were inspected or executed.

## Capacity must cover every writer

`reports/views.generate_report_action`, `jobs/core_workflows.dispatch` REPORT and `reviews/services.request_pack_artifact` all reach `create_report`/report jobs. `reports/jobs.ReportGenerationHandler` and the wrapped review handler converge at `artifact_services.persist_pdf_artifact`, which also remains callable directly. Only review freezing currently reserves capacity. Legacy assessment report jobs can materialize artifacts without a Review CapacityReservation; the review cap includes their existing metadata bytes but does not constrain their own new writes. Uncommitted external objects from process loss are not counted by that metadata sum.

Before advertising a storage or report quota, put a narrow admission/reservation boundary across every allowed creation path and bind persistence to its reservation; retain deterministic replay without charging/reserving twice. If legacy creation is outside launch scope, gate it explicitly and qualify its denial rather than claiming the shared writer alone enforces quota. Ordinary existing reports must retain authorized read/export.

The base CapacityReservation state is immutable `reserved`. Migration reviews/0002 projects the latest ReservationEvent for outstanding byte reservations, so a `consumed` completion releases the reserved-byte estimate while the artifact's actual bytes remain counted. Interval count still uses the immutable reservation row state. This currently counts every admitted reservation cumulatively toward 12, including consumed entries. That may be correct for an admitted-pack allowance; it must not silently become a refundable concurrency counter. Define whether a confirmed pre-effect cancellation restores an interval slot; unknown outcomes must hold bytes/slots until reconciled. No release receipt or cancellation issuer is currently present.

## Minimal safe proposed executor

Keep report, artifact, snapshot, request and original completion identities unchanged. Add an append-only object lifecycle ledger: `retained -> expiry_planned -> deletion_pending -> expired_confirmed`, plus `reconciliation_required`. Every event binds organization, artifact/report/request identities, original hash and size, exact internal key, storage backend/bucket identity, object generation/version where available, policy version, eligibility basis and database timestamps. A terminal receipt describes expiry of object availability, not removal of original evidence or customer resolution.

1. An operator-approved policy defines eligible objects and holds. A narrow planner runs a bounded database-clock batch under per-artifact/control/capacity serialization and records the exact deletion intent. No caller-supplied keys or arbitrary bucket operations. Exclude active writes/claims, ambiguous objects and explicit holds. Commit intent before external deletion.
2. A separately scoped cleanup process consumes only those intents. Do not grant ordinary app or existing worker broad delete/ledger authority. Role design remains subject to review; storage credentials should constrain the report prefix and required delete/read verification only. The database proves admitted intent binding, not remote deletion truth.
3. Delete the bound generation safely. Shared deterministic keys mean an expired object's key must never be repopulated by historical retries; add persistence/admission veto for expired identities. Without generation-conditional deletion, serialize legitimate writers and treat externally replaced/mismatched objects as reconciliation, never delete a different generation merely because the key matches.
4. Verify absence through a typed backend result. Timeout, permission denial, network error, versioning/delete-marker uncertainty or hash mismatch appends reconciliation and retains capacity. An authenticated not-found result can support confirmed expiry for the qualified backend contract. A later retry retains the original intent identity.
5. Append confirmed expiry and release retained-byte accounting atomically in the database. Account for object bytes through nonexpired availability projection, not by deleting immutable artifact metadata. Failed database commit after remote absence remains a durable pending intent recoverable by read-back. Read/download then returns an explicit expired state before storage access; history can retain minimal tombstone/receipt according to policy.

Unregistered objects left by failed uploads require a separate bounded orphan inventory/reconciliation contract. Do not delete an object absent from SQL automatically: transaction loss, delayed registration or restore can make it legitimate. Identify deterministic key + request/claim/intent, wait out qualified write/recovery windows and admit a distinct orphan-cleanup intent. Backups, replicas and versioned objects need their own retention/custody evidence; deleting the primary key does not prove erasure everywhere.

## Time, baseline and account semantics requiring decisions

- Define 12 months as calendar months or fixed days, and anchor completed history to verified completion or source capture. Using old captured_at alone could immediately expire a newly purchased historical review. Recommendation: completion/registration clock for available pack history; source evidence date remains visible separately.
- Active paid accounts receive rolling history under the agreed window. After paid lapse/termination, preserve the agreed read/export interval from the latest admitted paid endpoint (currently 90 days), subject to owner/customer binding. Do not apply a moving future paid-end grace to every old artifact of an active subscriber: that would defeat rolling retention indefinitely. Explicitly decide whether 90 days protects all remaining packs or only those within the rolling window at expiry.
- Suspend deletion when payment history/authority is ambiguous; do not infer expiry from missing authority pins, unavailable billing ingestion or a projection-only status. Resubscription must not resurrect already-expired objects or erase the original expiry receipt.
- Decide whether the currently selected baseline's evidence remains pinned, or expires with an explicit unavailable-baseline state requiring an owner-selected replacement. Never silently advance baseline, regenerate expired evidence under its old identity, or treat a tombstone as comparison inputs.
- Separate customer product history/object availability from security/audit, account identity, billing receipts and contractual/legal retention. Immutable metadata may itself contain sensitive data; its permanent existence is not an agreed privacy retention policy. These categories require an operator-approved policy and explicit future purge/tombstone design, not indiscriminate immutable-table deletion.
- Warning notices and complete export before expiry remain required product work. Product cleanup scheduling is a safety/infrastructure function, not customer Automation workflow entitlement; keep its authority separate.

## Qualification before enabling cleanup

Actual-role probes must deny raw lifecycle insertion, arbitrary keys, foreign tenants, premature expiry, missing paid-history basis and expired-object repopulation. Deterministic barriers must cover concurrent upload/completion, download versus planned expiry, two cleanup claimants and database rollback after successful remote delete. Storage tests must distinguish genuine absence, permission denial, network failure, lost delete response, replacement generation and versioned retention. Capacity tests must cover every legacy/review writer, exactly-once reservations, unknown outcomes retaining capacity and exactly-once confirmed byte release. Restore tests must reconcile expired receipts with restored database/object backups without reviving expired availability.

All allowance amounts above describe current scaffolding, not a confirmed offer or measured operating envelope. No executor should be enabled until the time/baseline/hold decisions and backend deletion contract are explicit and these finite candidate gates pass.
